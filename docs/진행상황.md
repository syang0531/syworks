## 1. 빌드 & 실행

JDK 21 설치됨: `C:\Program Files\Eclipse Adoptium\jdk-21.0.11.10-hotspot`. Gradle은 wrapper 사용.

```powershell
$env:JAVA_HOME = 'C:\Program Files\Eclipse Adoptium\jdk-21.0.11.10-hotspot'
.\gradlew.bat runData      # 모델·영문 lang·제작 레시피 생성 (아이템/합금 추가 시 필수)
.\gradlew.bat runClient    # 게임 실행 (GUI/렌더링은 이걸로만 확인 가능)
.\gradlew.bat runServer    # 헤드리스 검증 (레시피 파싱·등록 오류 확인용)
.\gradlew.bat compileJava  # 컴파일만
.\gradlew.bat build        # 배포 jar (build/libs/)
```

**⚠️ 로그 검증 함정**: PowerShell `Tee-Object` 로그는 **UTF-16(널바이트 포함)**. bash `grep`으로 오류 찾을 때 **반드시 `tr -d '\000'` 먼저** 안 하면 매칭이 조용히 실패해서 오류를 놓칩니다. (이번 세션에서 이것 때문에 합금 레시피 파싱 버그를 한동안 못 봤음.)
```bash
CLEAN=$(tr -d '\000' < "$LOG"); echo "$CLEAN" | grep -iE 'ERROR|Exception|Parsing error'
```
`runServer`는 스스로 안 꺼지므로, `Done (` 확인 후 java 프로세스 kill:
```powershell
Get-CimInstance Win32_Process -Filter "Name='java.exe'" | Where-Object { $_.CommandLine -like '*yame*' } | ForEach-Object { Stop-Process -Id $_.ProcessId -Force }
```

### ★ 데이터 주도 설계 (중요)
**새 금속/합금 추가 = enum 1줄 + 레시피 JSON + 텍스처 색상 1개.** 잉곳·장비 9종·제작 레시피·크리에이티브·영문이름·모델이 전부 자동 생성됨. (예: 백금 초합금은 `ModAlloy`에 한 줄 추가로 완성됐음.) 새 합금 추가 시 할 일:
1. `ModAlloy`(또는 `ModMetal`)에 enum 항목 추가
2. 합금 레시피 JSON을 `data/yame/recipe/`에 작성
3. `tools/gen_textures.ps1`의 `$colors`에 색상(+은회색이면 `$accent`에 점 색) + `$alloys`/`$metals` 리스트에 이름 추가 후 실행 (바닐라 철 틴팅으로 잉곳·도구·방어구·바디레이어 자동 생성)
4. `ko_kr.json`에 한글 이름 추가
5. `runData` 재실행

## 5. 마법 시스템 설계 (신규 계획 — 미구현)

> 금속/합금(장비 제작)에 이어 **마법** 축을 추가. 목표: **바닐라 전체 마법책 42종**을 룬 기반으로 제작 가능하게.

### 5.1 메커니즘

- 모든 작업은 **룬 제단(Rune Altar)** 에서 `base + catalyst → result` 단일 메커니즘으로 통일:
  - **룬 제작**: 금 주괴(base) + 청금석(catalyst) → **룬(Rune)**
  - **마법책 Lv1**: 재료 아이템(base) + 룬(catalyst) → 해당 마법책 Lv1
  - **레벨업**: 마법책 LvN(base) + 룬(catalyst) → LvN+1 (각 마법의 최대 레벨까지)
- 즉 **최대 레벨 책 1권에 필요한 총 룬 = 최대 Lv** (재료 아이템은 최초 1회만 소모)
- **재료 선정 기준**: 테마 적합 + "잘 안 쓰이거나 적당히 희귀". 필수 3종(Protection·Unbreaking·Mending)은 의도적으로 구하기 쉬운 재료로 낮춤.
- 룬 제단은 **연료 없음 + 모루식 즉시 방식**: 유효한 두 입력이 놓이면 결과가 **출력 슬롯에 즉시 미리보기**로 뜨고(대기·진행 화살표 없음), **꺼낼 때** base·catalyst 소모. 두 입력 슬롯은 **좌우 순서 무관**(어느 쪽에 재료/룬을 넣어도 동작). `LIT`(발광)은 유효 레시피가 놓여 있는 동안 켜짐.

### 5.2 만들어야 할 것

1. **기능 블록**: `룬 제단(Rune Altar)` — 재료+룬 조합 → 마법책 산출 (커스텀 레시피 타입 또는 조합 GUI)
2. **아이템**: `룬(Rune)` 1종
3. **레시피**: 룬 제작 1종 + 마법책 매핑 42종 (레벨업 단계 포함)

기존 데이터 주도 설계(§3 ★)와 동일하게 **enum/표 1곳 + 레시피 JSON**으로 확장 가능하도록 구현 권장.

### 5.6 구현 노트 (핵심 설계 결정 — 다음 세션 필독)

- **컴포넌트 정확 매칭이 핵심**: `ImbueRecipe`의 base/catalyst는 바닐라 `Ingredient`(아이템/태그만 구분)가 **아니라** `ItemStack` 정확 매칭(`ItemStack.isSameItemSameComponents`)이다. 인챈트북은 `stored_enchantments` 컴포넌트로만 Lv이 구분되므로, Ingredient였으면 "Sharpness I 책"과 "Sharpness II 책"을 구별 못 해 레벨업 체인이 깨진다. → 레벨업 레시피의 `base`는 이전 레벨 책을 컴포넌트까지 명시(§ `book_sharpness_2.json` 참고).
- **인챈트북 결과 JSON 형식**: `result.components["minecraft:stored_enchantments"] = { "levels": { "minecraft:<ench>": <lv> } }`. LvN 결과의 컴포넌트와 Lv(N+1) 레시피의 base 컴포넌트가 **바이트 단위로 동일**해야 매칭됨(동일 JSON이면 자동 보장).
- **stack count = 필요 수량**: base/catalyst의 `count`(생략 시 1)가 소모량. 룬 여러 개 요구하려면 catalyst count↑.
- **모루식 즉시 미리보기(진행 X)**: `RuneAltarBlockEntity.assembleResult()`가 부작용 없이 결과를 계산 → `RuneAltarMenu`의 출력 슬롯(`ResultSlot`)이 `broadcastChanges`마다 이를 동기화해 미리보기 표시. 꺼낼 때만 `consumeInputs()`로 소모(중복 방지: `remove()`가 항상 라이브 결과를 반환). cast time/ContainerData 제거됨.
- **좌우 순서 무관**: `ImbueRecipe.matches()`가 두 배치를 모두 검사(`baseMatches`/`catalystMatches` 헬퍼). `consumeInputs()`도 어느 슬롯이 base/catalyst인지 판별해 소모. base=재료/책, catalyst=룬/청금석은 서로 다른 아이템이라 모호성 없음.
- **LIT = 준비 상태**: 유효 레시피가 놓여 있으면 켜짐(블록광 7 + `ENCHANT` 파티클). FACING 없음(대칭). tick은 이 상태 동기화만 담당.
- **룬 제단은 마법부여대처럼 렌더**: 풀 큐브가 아니라 **3/4 높이(16×12×16) 커스텀 모델**(`ModBlockStateProvider.runeAltar()` — 바닐라 `enchanting_table.json`과 동일 element/uv). 떠 있는 책은 **`RuneAltarRenderer`(BER)** 가 바닐라 `BookModel` + `entity/enchanting_table_book`로 렌더(바닐라 `EnchantTableRenderer` 미러, 애니메이션만 gameTime 기반). `EntityRenderersEvent.RegisterRenderers`에서 등록. 풀 큐브로 하면 옆면에 검은 띠 + 책 안 보임 → 이 방식이 정답.
- **텍스처**: 바닐라 마법부여대 3면 리컬러. 곱셈 틴트는 흑요석이 검게 눌려서 **shadow-lift 방식**(`Recolor-Lift` — 어두운 픽셀도 `$raFloor`만큼 틴트 유지) 사용. 현재 값 `$raTint='4A78F0'`, `$raBase=130`, `$raFloor=0.48`. 색/밝기만 바꾸려면 이 값만 고치고 `gen_block_textures.ps1` 재실행(텍스처 PNG만 바뀌므로 `runData`/컴파일 불필요, 게임 재시작만).

### 5.7.0 설계 원칙 (확정)

- **마법은 책에, 원소·효율은 지팡이 재료에 귀속.** 지팡이 친화 원소와 마법 원소가 맞으면 보너스 → 하드락 없이 자연스러운 페어 유도.

- **마나 없음. 빈도 제한 = 쿨다운.** 내구도는 빈도 제한이 아니라 장기 유지비(시전당 1 소모, 기반 재료로 수리).

### 5.7.4 쿨다운 모델 (마나 없음)

- **마법별 개별 쿨다운.** 지팡이 `쿨감` + `친화 쿨감`이 곱연산 단축. 예: 일렉트럼(⚡친화)으로 뇌격 → 4s ×(1−0.35−0.25) = **1.6s**.
- **전역 쿨다운(GCD) 0.25s** 하나만 추가 — 마법 순간 전환 난사 방지용 최소 장치.
- 쿨다운 중 시전 실패(바닐라 아이템 쿨다운 스윕 오버레이 재활용). HUD에 현재 마법 아이콘 + 쿨다운 파이.

### 5.7.5 다중 마법 선택 (부여·선택 분리)

- **부여 — 모루**: `지팡이 + 마법책 → 지팡이(마법 추가)`, 책 소모 + 소량 경험치. 데이터 컴포넌트 `bound_spells:[id…]`에 추가, **슬롯 수까지만**(초과 부여 거부). 숫돌(Grindstone)에 넣으면 마법 전부 초기화.
- **선택 — 인게임**: **Shift+마우스휠**로 장착 마법 순환(새 GUI 불필요). 선택값은 `active_spell` 컴포넌트 + HUD/툴팁 표시. 폴리시로 키 홀드 방사형 메뉴 추가 여지(후순위).

### 5.7.6 제작·부여 전체 흐름

```
[책 제작] 재료 아이템 + 룬 ──(룬 제단)──▶ 마법책          ← 기존 ImbueRecipe 재활용
[지팡이] 검 재료(잉곳/나무 등) ──(제작대)──▶ ○○ 지팡이(빈 슬롯)
[부여]   지팡이 + 마법책 ──(모루)──▶ 지팡이(마법 장착)
[선택]   Shift+휠로 활성 마법 전환 → 우클릭 시전(쿨다운)
```

- **데이터 컴포넌트**: `bound_spells`(list), `active_spell`(id) — 인챈트북 `stored_enchantments` 접근과 동일 방식.

- 레시피 생성은 추출·합금·마법책 관례대로 `tools/*.ps1` 스크립트로 resources 직접 생성(datagen 아님). `gen_imbue_recipes.ps1` 패턴 재활용 가능(단, 결과가 인챈트북이 아니라 마법책 아이템).

### 5.7.8 확장 여지

## 6. 이번 세션에서 배운 함정 (다음 세션 필독)

- **`SizedIngredient`는 `FLAT_CODEC` 사용** — flat JSON `{"item":"...","count":N}`을 파싱하려면. `NESTED_CODEC`은 `{"ingredient":{...},"count":N}` 형식이라 불일치. (`AlloyRecipeSerializer.java` 참고)
- **커스텀 GUI 텍스처는 256×256** — MC `blit`이 256을 가정. 내용은 좌상단에 배치. (176×166로 만들면 확대·잘림)
- **1.21 화로 불꽃/화살표는 `furnace.png`에 없음** — 스프라이트로 분리됨: `minecraft:container/furnace/lit_progress`(불꽃), `container/furnace/burn_progress`(화살표). `guiGraphics.blitSprite(...)`로 그림. 단, 화로의 **빈 상태** 불꽃/화살표는 `furnace.png` 배경에 있음(그래서 합금로 텍스처에 그 픽셀을 합성함).
- **로그 UTF-16 널바이트** — §1 참고. grep 전 `tr -d '\000'`.
- **커스텀 블록엔티티 tick 진행도 로직 3분기** — (불O+처리O→진행), (불O+처리X→즉시0), (불X+진행>0→서서히감소). 바닐라 화로와 동일하게.
